## ADR-0001: 数据库连接池方案 (pgBocker)

**状态**: ✅ 接受 (计划中)  
**日期**: 2026-07-08  
**修订**: 2026-08-24  
**决策者**: 研发团队  
**影响范围**: 数据库连接层  

### 上下文
当前系统直连 PostgreSQL，IP 漂移时连接中断。需要连接池提升稳定性。

### 决策驱动因素
- DB IP 漂移导致连接中断
- 需要连接复用降低 PostgreSQL 负载
- 需要故障自动转移能力

### 备选方案
| 方案 | 优点 | 缺点 |
|------|------|------|
| **pgBocker** | 轻量、事务级池、故障转移 | 需额外部署 |
| Pgpool-II | 自带负载均衡、查询缓存 | 重量级、配置复杂 |
| 应用层池 | 无额外部署 | 无故障转移 |

### 决策
选择 **pgBocker**，轻量且满足故障转移需求，适合当前 Docker 环境。

### 后果
- **正面**: 连接稳定性提升，IP 漂移影响降低
- **负面**: 增加一个组件的运维成本
- **缓解措施**: 部署在同一 Docker network，使用健康检查监控

### 参考链接
- [pgBocker 官方文档](https://www.pgbouncer.org/)
- `docs/DB_CONNECTION_POOL_MONITORING.md`

## ADR-0002: 日志集中化方案 (Loki + Grafana)

**状态**: ✅ 接受  
**日期**: 2026-07-08  
**修订**: 2026-08-24  
**决策者**: 研发团队  
**影响范围**: 日志管理  

### 上下文
日志分散在各容器和文件中，故障排查困难。需要集中化日志管理。

### 决策驱动因素
- 日志分散难以排查
- 已有 Grafana 监控栈
- 轻量级方案优先

### 备选方案
| 方案 | 优点 | 缺点 |
|------|------|------|
| **Loki + Grafana** | 与现有 Grafana 集成、轻量 | 查询能力有限 |
| ELK | 功能全面、生态成熟 | 资源消耗大 |
| Filebeat | 轻量、易部署 | 需额外存储 |

### 决策
选择 **Loki + Grafana**，与现有监控栈集成，资源消耗低。

### 后果
- **正面**: 日志集中管理，与监控 Dashboard 统一
- **负面**: Loki 查询语法需学习
- **缓解措施**: 编写查询模板和常用查询文档

### 参考链接
- [Loki 官方文档](https://grafana.com/oss/loki/)
- `docs/LOG_CENTRALIZATION.md`

## ADR-0003: DB 健康监控方案 (Node.js 脚本)

**状态**: ✅ 接受 (已实现)  
**日期**: 2026-08-22  
**决策者**: 研发部高级研发专家  
**影响范围**: 数据库连接监控  

### 上下文
DB IP 在 172.23.0.2 ↔ 172.23.0.20 间漂移，需自动检测和恢复。

### 决策驱动因素
- IP 漂移导致连接中断
- 需自动发现新 IP
- 需指数退避重试

### 备选方案
| 方案 | 优点 | 缺点 |
|------|------|------|
| **Node.js 健康脚本** | 轻量、可自定义 | 需定期执行 |
| Docker healthcheck | 自动重启 | 无法处理 IP 漂移 |
| pgBocker | 自带健康检查 | 需额外部署 |

### 决策
选择 **Node.js 健康脚本** (`scripts/db-health-monitor.js`)，轻量且可自动扫描子网发现新 IP。

### 后果
- **正面**: IP 漂移 5 分钟内自动恢复
- **负面**: 需 cron/heartbeat 定期触发
- **缓解措施**: 集成到 heartbeat 每 30 分钟执行

### 参考链接
- `scripts/db-health-monitor.js`
- `docs/RUNBOOK_DB_RECOVERY.md`
